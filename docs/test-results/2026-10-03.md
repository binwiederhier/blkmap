## Problems found while getting here

All fixed before these runs, each with a test that failed first except where noted:

- **A fresh overlay adopted a stale live bitmap.** Deleting the cow file and bitmap to start
  over (what blkmap's own error message advises) left `/run/blkmap/<id>.bitmap` from a crashed
  server, the new bitmap adopted its bits, and the start was refused for a missing cow file.
  A freshly created bitmap now never adopts a live file.
- **Reload could exceed systemd's timeout.** On 6.8 under three unthrottled writers the
  handoff's flush took 100 s, past the 90 s reload limit. The handoff no longer flushes or
  waits: the cow page cache and the live bitmap outlive the exec.
- **Shutdown waited on a blocked hydration read** before aborting the source (review finding
  5). It now aborts first. The handoff no longer waits at all.
- **Group requests allocated per request** (`router.split`); now an iterator, pinned at zero
  allocations.
- **Kill test reached the crash-loop limit.** Three deliberate kills per 12 s cycle exceeded
  systemd's 10 starts a minute on a fast VM; the test now resets the start counter.
- **The first soak saturated box11.** Uncapped random writes into fresh chunks amplify through
  copy-up; with two soaks and a CI run the host's NVMe hit 70% I/O pressure and the test VMs'
  own root disks stalled. The fio writers are now capped at 150 IOPS. Without the cap's load
  box11 idles near 20% pressure from its other VMs; with both capped soaks it stayed near 5%.
- Infrastructure: a force-destroyed CI VM left its ZFS volumes on `tank`, which made the next
  clone fail; they were removed.

Not reproduced: one 6.8 run had `stop_during_hydration` take 14 s (six repeats took under 0.4 s).
A stop slower than 2 s now logs how long it spent draining, flushing and deleting; the
scenario prints that on failure.

## Headline benchmark on codebox (12 vCPU, kernel 6.8.0-139) at 01:16 UTC, commit b2fcdf6

Zero-backed 4 GiB device, fio io_uring, direct I/O, 4 jobs at depth 32 (1M sequential: one
job at depth 16), 8 s each, cow file on the virtio root disk (`/tmp`):

| workload | result |
|---|---|
| 4K random read | 4,640 MiB/s, 1,187,982 IOPS |
| 64K random read | 24,248 MiB/s, 387,968 IOPS |
| 1M sequential read | 10,494 MiB/s |
| 4K random write | 195k IOPS median of 4 runs (176k to 200k); 515k with the cow file on tmpfs |

The binary of the README's previous table (commit c82546f6, 2026-10-02 02:19) measured in the
same session gives the same write numbers (176k to 205k on disk, 483k on tmpfs), so none of
the later changes (dispatch latch, flush ordering, groups, writeback, recovery) cost
single-device write throughput. One run of the current binary dropped to 50k IOPS when the
5 s periodic fdatasync of a few GiB of dirty cow data landed inside the 8 s window; the
previous table's 86k was most likely the same effect.
